- **Hypothesis**: The query has no WHERE clause (`SELECT count(*), sum(value) FROM bench.db.f_evolved`), making runtime pruning structurally impossible (`predicate_tasks = 0`, `files_pruned = 0`). The 10 ms slowdown (base_on 81 ms vs cand_on 91 ms; cand_off 80 ms vs cand_on 91 ms) is caused by native scan compute variance during schema evolution adapter execution (type promotion of `int32` to `int64` in `f_evolved`).
- **Evidence**:
  - `results-layouts.jsonl`: `native_iceberg_scans = 1`, `num_splits = 13`, `bytes_scanned = 22,257,072`, `output_rows = 8,000,000`. `predicate_tasks = 0`, `files_pruned = 0`, `rg_pruned = 0`.
  - Stage timings: `elapsed_compute` for `CometIcebergNativeScanExec` in candidate_on round 1 rep 1 spiked to 163 ms (median 100 ms) due to Arrow schema adapter casting.
  - Plan diff: Structurally identical physical plan (`CometColumnarToRow` -> `CometHashAggregate` -> `CometExchange` -> `CometHashAggregate` -> `CometIcebergNativeScanExec`).
- **Competing Explanations**: Driver GC (disproven: `driver_gc_ms = 0`), JIT regression (unsupported by profiling evidence).
- **Later Commits**: `434d18333` / `8cd4d9a98` do not alter the int32->int64 schema evolution path; behavior is governed by `SparkPhysicalExprAdapterFactory`.
- **Concrete Fix Proposal**: Short-circuit `CometHashAggregateExec` count-only scans or fastpath identity/widening casts in `SparkPhysicalExprAdapterFactory` (`native/core/src/parquet/schema_adapter.rs:45`).
- **Risk & Expected Gain**: Low risk; ~10 ms reduction on schema-evolved aggregation scans.
- **Validation Query List**: `count_all__f_evolved`, `count_all__f_part_evolved`.

### 2. Queries with Pruning Benefit Below Parity (`cand_on / cand_off < 1.0`)
- **Analysis**: Queries such as `count_all__f_sorted` (0.91x [0.83, 0.97]), `count_all__f_many_files` (0.94x [0.88, 0.99]), and `count_all__f_big` (0.96x [0.93, 0.99]) exhibit `cand_on` taking slightly longer than `cand_off`.
- **Root Cause**: When `spark.comet.exec.aggregate.dynamicFilter.enabled=true`, the planner inspects partial aggregations to see if min/max dynamic filters can be constructed (`IcebergMinMaxFilterExec::try_new`). Although it returns `None` for count/sum aggregates, the wrapper checks, atomic filter provider registrations, and task listener overhead impose ~2-6 ms of fixed latency, which is measurable on fast 80-200 ms queries without producing any pruning benefit.

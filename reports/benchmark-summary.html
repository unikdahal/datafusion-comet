3. Correctness

  • Candidate: 0 result mismatches in every campaign — 403 timed queries × 4 variants × 8 rounds, plus 4,000 randomized fuzz queries per campaign (NaN, ±0, nulls, deletes, schema evolution).
  • Apache main (baseline) returned wrong results on broadcast joins with string keys built from a DISTINCT (sliced Arrow buffers corrupted during broadcast). Reproduced in an isolated test, root-caused, fixed in the fork, and filed as fork issue #42. Those queries are excluded from timing comparisons.
  • Defects found and fixed in our own branch before release: NaN / signed-zero handling in a row-filter shortcut, delete-file loading continuing after cancellation, an over-eager shuffle-probe optimisation (reverted), a row-filter gating change that regressed selective queries (reverted after measurement).

4. Where we are not faster (and why)

  • TPC-H (0.99×): join keys are not correlated with the physical sort order, so there is nothing to prune; the result shows the pruning machinery costs ≈ nothing when it cannot help.
  • Large non-selective joins (strjoin 1.00×): filters remove few rows; an adaptive bypass now switches filtering off when it is not paying for itself.
  • 22 queries with a confidence interval below 1.0× in this single campaign (0.90–0.98×, mostly sub-100 ms queries). None reached the harness’s 0.90× regression threshold. Policy: a regression counts only if it reproduces in two independent campaigns — several earlier “regressions” disappeared on re-measurement (e.g. 0.88× → 1.03×).

5. Methodology

Variantsbaseline (Apache main) and candidate (fork), each with runtime pruning on and off — 4 variants per query
Repetition8 balanced JVM rounds per variant (order rotated), 4 warm-ups per query, raw per-run timings kept
Statisticsmedians; bootstrap 95% confidence intervals on the speedup ratio; suite geomeans
Fairnesssame data files (byte-identical), same queries, same Spark configuration; baseline and candidate always run on the same machine for a given query; per-query operator coverage compared
Correctness gateevery result compared with plain Spark; mismatching comparisons are excluded from speedups
InfrastructureGitHub Actions, 18 parallel shards; campaign wall time cut from ~4 h to 1 h 46 min with identical protocol
Caveatsshards run on different CPU models (AMD EPYC 7763 / 9V45 / 9V74, Intel Xeon 8370C) — ratios within a shard are paired, cross-campaign ratios of very fast queries vary with CPU; compare bytes/rows read for those
